# SmartFridge

A study project exploring how to build a clean REST API with Java and Spring Boot. SmartFridge keeps track of the food stored in a refrigerator and suggests a recipe built from the ingredients that are actually available.

The focus is on learning backend fundamentals in practice: layered architecture, DTO boundaries, entity mapping, partial updates, meaningful HTTP semantics, and calling an external AI API from a Spring service.

## Current Features

- Full CRUD for food items over a REST API
- Food items modeled as JPA entities, persisted with Hibernate
- Ingredient categorization through a `FoodCategory` enum
- DTO layer, so database entities are never exposed in HTTP payloads
- Explicit entity/DTO mapping through a dedicated mapper component
- Partial updates via `PATCH`: fields omitted from the request body keep their stored values
- `404` responses for operations on identifiers that do not exist
- Schema managed by versioned Flyway migrations, not generated by Hibernate
- Data persisted in PostgreSQL, so it survives application restarts
- AI recipe generation: the stored food items are turned into a prompt and sent to the OpenAI Responses API through `WebClient`
- Only the recipe text is returned to the client, not the provider's response envelope
- The OpenAI credential is read from the environment, never hardcoded

## Technology Stack

- Java 17
- Spring Boot 4.1.1
- Maven (with the bundled Maven Wrapper)
- Spring Web MVC (HTTP layer)
- Spring WebFlux / `WebClient` (outbound call to OpenAI)
- Spring Data JPA / Hibernate
- PostgreSQL
- Flyway
- Jackson (`JsonNode`, for reading the OpenAI response)
- Lombok

Spring Boot 4 splits the old `spring-boot-starter-web` into narrower starters, so the
dependencies are declared as `webmvc`, `webflux` and `webclient` instead.

## Domain Model

A `FoodItem` holds:

| Field            | Type           | Notes                                  |
| ---------------- | -------------- | -------------------------------------- |
| `id`             | `Long`         | Generated by the database              |
| `name`           | `String`       | Item name                              |
| `category`       | `FoodCategory` | Stored as a string                     |
| `quantity`       | `Integer`      | Wrapper type, so `null` means "unset"  |
| `expirationDate` | `LocalDate`    | Used to prioritize ingredients         |

Available categories: `FRUITS`, `VEGETABLES`, `DAIRY`, `RED_MEAT`, `WHITE_MEAT`, `GRAINS`, `PASTA`, `BREADS`, `SWEETS`, `BEVERAGES`, `SNACKS`, `SEAFOOD`, `OTHER`.

## API

### Food items — base path `/food`

| Method   | Path         | Description                  | Responses            |
| -------- | ------------ | ---------------------------- | -------------------- |
| `POST`   | `/food`      | Create a food item           | `200`                |
| `GET`    | `/food`      | List all food items          | `200`, `204` if empty |
| `GET`    | `/food/{id}` | Get a food item by id        | `200`, `404`         |
| `PATCH`  | `/food/{id}` | Partially update a food item | `200`, `404`         |
| `DELETE` | `/food/{id}` | Delete a food item           | `200`, `404`         |

Create an item:

```bash
curl -X POST http://localhost:8080/food \
  -H "Content-Type: application/json" \
  -d '{"name":"Milk","category":"DAIRY","quantity":2,"expirationDate":"2026-10-15"}'
```

Any `id` sent in the request body is ignored on creation; the database assigns it.

Update only the quantity, leaving every other field untouched:

```bash
curl -X PATCH http://localhost:8080/food/1 \
  -H "Content-Type: application/json" \
  -d '{"quantity":5}'
```

### Recipes — base path `/recipe`

| Method | Path      | Description                                       | Responses    |
| ------ | --------- | ------------------------------------------------- | ------------ |
| `POST` | `/recipe` | Generate a recipe from every stored food item     | `200`, `204` |

The endpoint takes no request body: the ingredients are whatever is currently in the
fridge. The response is the recipe as plain text.

```bash
curl -X POST http://localhost:8080/recipe
```

## Getting Started

### Prerequisites

- Java 17 or higher
- A running PostgreSQL instance
- An OpenAI API key
- No local Maven install required — use the wrapper

### Database

Create the database once; Flyway creates the tables on the first run:

```sql
CREATE DATABASE foods;
```

### Configuration

Credentials are read from the environment, so they are never committed. Copy the
example file and fill in your own values:

```bash
cp .env.example .env
```

```dotenv
DATABASE_URL=jdbc:postgresql://localhost:5432/foods
DATABASE_USERNAME=postgres
DATABASE_PASSWORD=your-password

OPENAI_API_KEY=your-openai-key
```

`.env` is git-ignored. Real environment variables take precedence over it, which
is what a deployment would rely on. All four variables are required: an unresolved
placeholder fails the startup instead of surfacing later as a broken request.

The OpenAI base URL lives in `application.properties` (`openai.api-url`), since it is
configuration rather than a secret.

### Run

```bash
./mvnw spring-boot:run
```

On Windows:

```powershell
.\mvnw.cmd spring-boot:run
```

The API becomes available at `http://localhost:8080`. On startup Flyway applies
any pending migration and Hibernate validates that the entities match the
resulting schema, so a mismatch fails fast instead of corrupting data.

## Design Notes

These are the decisions worth explaining, since they are the point of the exercise.

**Entities are not exposed over HTTP.** `FoodDTO` defines the API contract while `FoodItem` maps the database table. Keeping them separate means a schema change does not silently break API clients, and clients cannot write to fields they should not control.

**The id only travels outward.** Entity-to-DTO mapping copies the `id`; DTO-to-entity mapping does not. Since `save()` performs an upsert keyed by `id`, accepting an id from the request body would let a `POST` overwrite an existing row instead of creating one.

**Partial updates read from the request and write to the stored entity.** `PATCH` loads the current entity, then copies over only the non-null fields from the incoming DTO. `quantity` is an `Integer` rather than an `int` precisely so a missing field is distinguishable from a legitimate zero.

**Existence checks avoid loading data they do not need.** Deletion uses `existsById` instead of fetching the full row, and returns a boolean so the controller can answer `404` instead of failing silently.

**The schema has a single owner.** Flyway creates and evolves the tables; `ddl-auto` is set to `validate`, so Hibernate never alters anything and only checks that the entities still match. Adding a field therefore means writing a new migration, not editing the entity and hoping. Applied migrations are immutable: Flyway stores a checksum for each one, so a change to a file that already ran is rejected instead of silently diverging from the database.

**The OpenAI call goes through `WebClient` directly, not Spring AI.** The base URL and the `Authorization` header are configured once in a `WebClient` bean, so `OpenAiService` only describes the request it wants to make. Doing the HTTP call by hand is the point here: it makes the request/response shape of the provider explicit instead of hiding it behind an abstraction.

**The provider's envelope stops at the service boundary.** The Responses API answers with a nested structure (`output` → `content` → `text`). `OpenAiService` walks it and returns a `Mono<String>` holding just the recipe, so the controller and its clients never depend on OpenAI's payload format. If no text is found, a readable fallback message is returned instead of an empty body.

**The prompt is built from the data, with constraints.** The stored items are formatted as a list carrying name, category, quantity and expiration date, and the prompt restricts the model to those ingredients plus basic staples, asks it to respect the available quantities, prioritize what expires first, and refuse to invent a recipe when the ingredients are not enough. Today's date is injected so "closest to expiring" is actually computable.

**The recipe controller returns a `Mono`.** The MVC layer handles the reactive return type through an async dispatch, so the request thread is not blocked while the model is generating. The rest of the application stays blocking, which is what JPA wants.

## Roadmap

- Input validation (`spring-boot-starter-validation`, constraints on the DTO, `@Valid`), splitting `FoodDTO` into separate create/update/response DTOs so `POST` and `PATCH` can carry different rules
- Centralized error handling with a consistent error response format, including failures coming from OpenAI
- Return `201 Created` on `POST`, `204 No Content` on `DELETE`
- Timeout and retry policy on the OpenAI call
- Automated tests for the service and controller layers, with the OpenAI call stubbed
- Expiration tracking and alerts for items close to their expiration date
- Recipe suggestions filtered by dietary preferences and restrictions
- Selecting which items go into the recipe, instead of always using the whole fridge

## Known Gaps

Being a study project, some rough edges are intentional and tracked above rather than hidden:

- No request validation, so invalid data (empty names, negative quantities) is accepted
- Missing fields on `POST` return `500` instead of `400`. The schema declares `name`, `category`, `quantity` and `expiration_date` as `NOT NULL`, but nothing rejects nulls before the insert, so the database constraint is what fails and the error surfaces as a server fault. Fixing this needs more than annotations on `FoodDTO`: `null` means "field missing, reject" on `POST` and "field omitted, keep the stored value" on `PATCH`, so a single validated DTO cannot express both. The way out is either validation groups or separate create/update DTOs. The same applies to `name` exceeding `VARCHAR(255)`.
- Error responses return plain text while successful responses return JSON
- No automated test coverage yet
- Failures from OpenAI (invalid key, rate limit, timeout) are not handled, so they surface as a generic `500`
- The model name is hardcoded in `OpenAiService` instead of being a configuration property
- An empty fridge still sends a request to the model; there is no short-circuit before spending a call
- `POST /recipe` is a `POST` without a request body, chosen because the call is not idempotent and has a cost; it will need a body once ingredient selection and dietary filters exist
- No caching, so asking twice for a recipe over the same ingredients pays twice
